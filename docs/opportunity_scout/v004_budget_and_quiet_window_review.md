# V004 R2 combined-budget and account-monitoring methods

Design review only. No method below authorises a CLI invocation, token-counting API request, account change or hosted probe. The existing V003 and fictional records remain unchanged.

## Complete-input admission method

Inventory and freeze the exact serialized user payload, explicit system prompt, full two-card schema, condition instructions, eligible evidence/memory, cutoff, transport flags, environment controls and implementation/executable/model identity. Record byte lengths and hashes for reproducibility and IO limits **only**. Audit any payload projection field by field: proof that the evidence/memory/cutoff/instructions are retained must precede removing audit duplication. The entire original card schema and lane/citation/semantic validation remain in scope.

Separate the following quantities for each potential internal request `j`:

- `K_j`: a model-specific token upper bound for **all known content** in that request, including message framing and any earlier generated history. Counting fields independently can miss boundary/framing effects; count/bound the complete actual serialization.
- `S_j`: a supported upper bound for CLI-added and provider-added scaffolding not included in `K_j`. Classify CLI and provider portions separately. Their being small in previous observations is not a bound.
- `J_max`: an independently supported maximum number of model requests/generations contributing to this attempt. One parent process, max turns 1 and one visible message ID do not establish it.
- `Y_j`: a supported output-token upper bound per internal request, including whatever thinking is included in reported output. A requested setting is not automatically an enforced guarantee.

The revised allowance is **60,000 combined tokens per attempt**, counting ordinary input, cache creation, cache reads and output. Approximately 20,000 total output tokens is a nonbinding planning guide, not a target, minimum, reserved split or separate ceiling. Detailed reasoning and the full evidence/schema requirements are preserved. Spending more than that output guide can still comply when the combined total is within the allowance.

The strict admission proof would require all quantities to be certified for the pinned complete interface and satisfy:

`sum(j=1..J_max, K_j + S_j + Y_j) <= 60,000`.

Any missing bound, unspecified coverage, unsupported tokenizer or unbounded continuation history produces **UNKNOWN**, not zero or a guessed margin. Record source/version/hash and exact scope of each purported certificate. Conditional arithmetic using assumed numbers is not independent certification. Under the examined subscription interface, `K_j` is not certified, both scaffolding bounds are UNKNOWN and `J_max` is UNKNOWN. Therefore the defensible strict pre-dispatch result is **BLOCKED / DO NOT DISPATCH**. A token certificate for just our prompt would not resolve the other missing bounds.

Do not derive a tokenizer guarantee from UTF-8 bytes, words, an OpenAI tokenizer, context-window size or three fictional averages. Anthropic's separate [token-counting interface](https://platform.claude.com/docs/en/build-with-claude/token-counting) describes its result as an estimate and may include system-added tokens. It does not expose the subscription CLI's complete hidden request; no token-counting endpoint was called. Adopting one would be a separately reviewed data transmission/authentication/interface choice, even if no generation charge applied.

For Path B, retain the same inventory, but label a token forecast **ESTIMATE** with its method/limitations or **UNKNOWN** if none is justified. A local byte ceiling can reject excessive IO; it cannot certify the combined allowance. Owner consent must explicitly permit uncertainty/possible excess before dispatch. Reconcile reported totals afterwards, retain all consumption/effort from failures, and stop on the preregistered triggers. These are compliance and risk decisions, not retrospective proof of resource prevention. Do not reserve a fixed input/output split or borrow tokens between attempts.

Proposed Path B allows at most two **visible** model generations: initial output plus one evidenced append-only output-limit continuation within the same parent invocation. The second request can reread context and add generated history, so its ordinary/cache input and output also count against the same 60,000. No second parent call, complete-answer regeneration, schema repair, semantic revision or third generation is authorised by this rule. A common supported CLI output setting must be frozen in the future package; this design review does not activate one or assume the CLI prevents overruns.

The offline `v004_budget_review.py` evaluates reported terminal components under R2, retaining UNKNOWN and conflicting subcounts. Thinking and nested cache-duration details are not added twice. Its status is arithmetic about reported usage only, never permission or proof of complete provider consumption. Actual attributable subscription charges, CLI list-price estimates and token consumption are different records. Do not infer zero charges or prorate a subscription fee from token counts.

No stream watchdog, kill-on-second-ID, time limit or dollar cap closes the strict proof gap: the next provider request or already-buffered output can precede detection/cancellation. A tool-permission hook is not a universal pre-model-request interceptor. `UserPromptSubmit` can block submitted/autonomous prompts, but coverage of every within-turn continuation/repair request was not established; a hook must not be promoted to `J_max=1` on that assumption. No hook or proxy is installed here.

## Quiet-window procedure for a separately authorised future validation

**Historical result:** the old end-of-window boolean and later file/process observations cannot reconstruct a missing per-file baseline or identify the writer. A separately running development Claude process is a plausible competing cause. The historical attribution stays UNKNOWN; unrelated metadata movement does not establish credential leakage. This is analytically unresolved, not a reason to read credentials or restore account files.

A future owner decision should distinguish accepting that historical limitation from requiring new prospective observations. A new clean observation cannot prove who caused the old change. If definitive historical attribution is a prerequisite, the available records cannot meet it.

1. Owner arranges a quiet window, voluntarily closing development Claude/IDE Claude activity and scheduled jobs. The assistant does not terminate processes, log out, edit settings, copy credentials or switch accounts. If activity cannot be paused, classify the window contaminated/unobservable and do not proceed.
2. Record a fixed watch list covering default-path state `.claude.json`, development settings/credential-store metadata, research settings/credential-store metadata, and plausible relocated config-state paths. Distinguish default/shared state from account-specific evidence; a path name alone does not attribute its writer.
3. For every watched file, collect **stat/lstat metadata only**: existence/type, size, nanosecond modification/change times, file identity and device; record sample timestamps. Reject links/junctions, unsupported types or inaccessible observations. Never open, decode, hash or copy credential/config contents. Store monitoring artifacts only under a new ignored Scout audit directory, never inside either account.
4. Collect process metadata with read-only OS queries before, during and after: Claude PID, creation time and parent PID; record enumeration coverage/failure. Never collect command lines or environments, which can contain prompts/secrets. Treat all non-probe Claude processes as potential development/concurrent activity. PID plus creation time prevents PID-reuse confusion. Enumeration cannot rule out every renamed/transient/helper process; disclose coverage.
5. Establish a 60-second no-CLI baseline, sampling files/processes every five seconds, then capture immediately before **each** separately authorised local inspection command and probe. A pre-existing process or metadata movement rejects the window. Do not quietly reset the baseline after drift or after authentication inspection.
6. Only with separate explicit fictional-probe authority, record the one parent-created probe's PID/creation/parent identity and fresh directory/UUID. Capture per-file/process snapshots immediately before launch, every five seconds during it, immediately after exit and through a 60-second cooldown. The permitted probe must be absent in idle baselines/cooldown; any other Claude process contaminates the window. Read-only safe authentication metadata should verify the CLI's echoed configuration directory against the requested research directory; do not infer this solely from our requested environment variable. No authentication command runs in this review.
7. Compare every adjacent sample **and the original baseline** across the whole sequence, with a separate before/after pair for each command/probe. Preserve all snapshots, observed changes, errors and process lifetimes. On change or unknown coverage, stop future dispatch; never restore bytes/timestamps, suppress a drift flag or retry the scientific slot. Explicitly label clean metadata during an observed window versus proven non-interference.

The new offline `v004_monitoring.py` provides metadata-only fixed-path snapshots and conservative comparison/window review. It never launches Claude, samples a process list, changes files, runs sleeps or authorises a probe. Tests use temporary fictional files and supplied process samples, including concurrent development activity, PID reuse, inaccessible paths and a permitted probe confined to the active sample. This makes the review reproducible without running the procedure now.

**Monitoring limits:** stat equality does not prove content equality, atomic multi-file snapshots or lack of between-sample writes. Writer attribution would require separately authorised OS-level event instrumentation and still might not resolve old events. No such instrumentation, account mutation or credential-content access is performed or implied.
